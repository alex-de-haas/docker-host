# A clean execution architecture for providers and Harness

## Decision proposed

Build a new execution protocol and a single implementation of native supervision shared by the first-party providers. Run one supervisor for each active attempt, on the host that launches it. The supervisor owns the native execution boundary, the adapter and the evidence that execution has ended. Provider applications retain independent installation, accounts and capability discovery. Harness owns the conversation and the user's intent. Core owns workspace resources and authority. Core remains usable without Harness or any execution provider.

The owner authorized a clean start on 2026-11-25. Old conversation, execution, receipt and projection data need no migration. Develop and qualify the replacement on empty stores. Retire the old protocol and implementation at cutover. Source worktrees, user files, account credentials, installation settings and unrelated application data have independent owners. This proposal does not schedule a production deletion.

## Why this boundary

The [two-week incident review](../../reviews/2026-11-25-provider-harness-reliability.md) traced failures both before and after provider extraction. Several arose when the native Worker, provider store, Harness and browser each decided whether the same run had ended. Others came from coupling new work to historical storage or testing a different launch environment from the shipped one. Provider extraction also demonstrated a valuable property: a native agent could finish while Harness was offline.

| Candidate | Consequence |
| --- | --- |
| Return all native execution to Harness | One local owner is attractive. Harness would again carry vendor runtimes/accounts, its update would affect execution, and independent consumers would require a chat application to run agents. It also leaves the original shared-history failure mode to solve. |
| Operate one mandatory neutral daemon per host for every provider | One host inventory and shared resource limits are useful. This introduces an additional service, RPC, trust boundary and common outage for independently installed providers. It would still need per-attempt containment and a vendor adapter. |
| **Ship the same supervisor with each provider and instantiate it per attempt** | A single codebase defines launch, accounting and stop. Each native attempt has one physical owner and each provider has its own failure and credential boundary. Replacing the provider HTTP process leaves a running attempt supervised. A vendor adapter translates native events and control. It cannot implement a second run state machine. |

A separate host-wide scheduler is unnecessary for this model. If an independent remote implementation exposes the new interface, it must identify its own termination boundary and pass the relevant conformance profile. A provider with best-effort remote cancellation can offer that disclosed capability to compatible callers. Work requiring verified workspace writers is admitted only on a profile that can actually enforce it.

## Objects and owners

| Object | Owner | Durable meaning |
| --- | --- | --- |
| Conversation, draft, queued input, attachment version, delegated chat assignment | Harness | What the user submitted and wants to see, with stable turn and attempt references. A stopped attempt does not close the chat. |
| Attempt | Provider, with one live supervisor | One admissible execution of one immutable input. Its ID is chosen before sending. Its desired state can move once from run to stop. Its observed phase, end reason, process scope and last observation are independent columns. A closed ID can never launch again. |
| Decision and effect | Attempt supervisor and the dispatcher that can cause the effect | Which gate was open, whether dispatch was prevented, which request crossed the boundary and which outcome the receiver established. |
| Workspace, allocations, source claims, sandbox and active development binding | Core | Which selected resources may receive new writers, which physical users remain, and whether removal is complete. A directory or a PID alone is insufficient ownership evidence. |
| Task and independent delegated execution | Task owner or Harness, as applicable | Parent, attempt, wait and delivery identity. Native children are inside the parent's execution boundary. A separately delegated chat has an explicit lifetime and its own attempt. |

Use one local transactional execution database **per provider installation**. Store attempts, idempotent command receipts, decisions/effects and ordered events in that database. The supervisor is the only producer of native observations for its attempt. Admission and stop may set the desired state transactionally while supervision is offline. One transaction records each state transition, allocates its event sequence and records any command receipt. Snapshot, status and event stream read the same committed data. A consumer reads a snapshot and its cursor from one transaction and resumes after that cursor. Index active attempts and due operations. Avoid walking old executions to admit new work. Use a local crash-tested configuration with durable acknowledgement and bounded event retention. [SQLite atomic commit](https://sqlite.org/atomiccommit.html)

Harness has its own chat database. It durably accepts a turn with its input and immutable attachment references, stores its outbound attempt ID, and submits that exact request until the provider acknowledges it or stop supersedes it. Persist received transcript content and its run cursor in one transaction. The UI can fetch current status even during a historical backfill. Browser cursors page the consumer's canonical transcript. A receiver resuming an unacknowledged stream reads the missing ranges from the provider's durable delivery queue. Preserve usage sequence and task accounting separately from current status. Historical repair cannot rewind a newer attempt, synthesize a decision or suppress live events. Neither service writes the other's database.

Execution phases are reserved, live, closing and closed. End reasons include completed, user stop, refused before launch and failure. An unreachable owner yields last-observed phase and observation time. It cannot advance phase. An indeterminate tool result is never an execution phase.

The public control vocabulary is small. Submit(attempt, immutable input) admits once. Stop(attempt) sets desired state even if Submit has not arrived. Decide(attempt, gate, decision ID, answer) succeeds only while that gate is open and returns its stored receipt on exact replay. Read(attempt) returns observed state, desired state and cursor. Events(after cursor) delivers facts in committed order. Same identity with different immutable input is rejected. Repeating Stop expresses the same monotonic intent with no revision supplied by the browser. Configuration edits can retain their own optimistic concurrency. Cancellation, deletion and detached cleanup each have an addressable status.

## Protocol at the difficult boundaries

**Launching and losing the acknowledgement.** Commit the reservation and deterministic supervisor/scope identity before native code may execute. Create an exclusive OS-backed supervisor instance for that attempt and a gated execution unit. Register the unit, recheck desired state and release the gate only if still entitled to launch. A concurrent Stop wins either before launch, or by finding and closing the registered unit. On supervisor or service restart, discover the exact unit and reattach, or prove its closure. A missing heartbeat or a reused PID cannot authorize a second launch. If the crash makes it impossible to tell whether inference already began, close the attempt as interrupted after proving containment. Keep the conversation usable and do not silently repeat its cost or effects.

**Enforcing a stop.** Immediately close pending decision gates and cancel automatic continuations on the stopped attempt. Drain the agent's output and issue a bounded cooperative interrupt. Record confirmed agent exit and close its conversation slot. Clean up descendants in the background and verify each physical claim at the point of release or exclusive reuse. Store the end reason as user stop. Normal completion additionally needs an actual final answer or a typed failure and completion of required native children. An early root result, idle observation or EOF is insufficient by itself. A deadline can trigger escalation or a failed attempt, but cannot certify that a surviving process is gone.

Qualification must show what happens when the supervisor itself dies. Candidate primitives include a Windows Job Object with controlled membership and handles, and a Linux execution unit under a delegated cgroup or container. Prevent escape through unsupported subprocess launch paths. On macOS, qualify the native agent exit and process-group cleanup path. Ordinary edits use this path. An operation that requires exclusive access must verify the resource before reusing it. Preserve supported native login and host-specific capabilities by qualifying them explicitly. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

**Dispatch and the lost result.** The gate owner serializes Allow and Stop. A pending approval is recorded as cancelled before dispatch only when the owner can guarantee that the command cannot be sent later. The dispatcher records the call ID and dispatch intent before contacting an external service. If delivery becomes ambiguous, query by the service's idempotency key, or record an indeterminate external outcome if it offers no such facility. A crash between durable dispatch intent and actual transmission is also ambiguous. Never repeat a non-idempotent command to determine whether it succeeded. Close the run once its execution boundary is closed. Keep any replay restriction on the specific operation or dependent resource. The screenshot fixture must finish with a stopped chat and an inactive approval card in both the prevented and the already-dispatched cases.

**Interrupted services and credentials.** Replace browser recovery and chains of component-specific retry commands with a bounded reconciliation loop at each owning service. Work is simply a committed desired state or an undelivered owner operation whose observed outcome is outstanding. A startup scan of an indexed due set, dependency-change wakeup and a low-rate scheduled pass all call the same idempotent operation. Persist next attempt and last reason. Apply limits, backoff and jitter. A second worker may take over after acquiring ownership, without launching an old attempt again. Separate user input, control and history capacity. Classify a transport failure during renewal separately from an actual revocation, an expired grant, an enforced deadline or an explicit workspace Stop. A transient telemetry failure cannot issue a cancellation. Continue already-authorized work only within its valid authorization window, suspend new privileged dispatch while authorization is uncertain and enforce a verified revocation or the actual expiry at the supervisor. Register resources attached mid-run under the same attempt identity. Retain narrowly scoped authority to finish an already accepted cleanup under current policy. Revalidate identity and grants for new invocation. Genuine account changes or newly authorized disclosure still use the owner's consent flow.

**Storage or host loss.** Isolate an invalid record to its attempt. If an entire provider database or disk is unavailable, suspend new dispatch for that installation, perform a best-effort physical stop of known owned live units when requested, and report durable acceptance only after writing succeeds. Other provider installations, chats and Core remain usable within their own dependencies. When storage returns, apply outstanding accepted intent and reconcile exact physical scopes. A verified restart of the execution host can establish local process loss within that boot's boundary. It says nothing about an external job. When evidence is irretrievable, record the loss and protect only potentially shared writers or non-repeatable effects. User-visible recovery can mean ending a failed turn and allowing a fresh turn. It does not require recovering the model's lost answer.

**Delete while work is in progress.** Chat Delete commits the exact selection, tombstone and cleanup references in Harness. The item leaves normal navigation and stops accepting work as soon as that transaction succeeds. Old responses cannot resurrect it. Core accepts a confirmed workspace selection in its own operation, fences new allocations and records the teardown steps. A combined selection persists the selected chat IDs before source removal and delivers both owner commands from the server. It survives a closed tab, restarts, a down provider and partial filesystem removal. Confirmed unfinished or dirty work is a supported case. Deleting a chat retires its owned execution and history while other chats, shared workspaces, published work and ordinary application data retain their lifetimes. Purge private payloads and retain minimal non-content cleanup handles only for the required period.

Core must handle a live app or Core itself consuming a selected worktree. Preflight the supported replacement/Return and include any affected service in the original confirmation. Persist the intent, verify the replacement is healthy and only then retire the old target and remove the source. If recovery would require changing permissions, replacing user data or switching an unrelated system outside that confirmation, report the exact external prerequisite. Unknown arbitrary processes are never signalled on PID or lease alone. Use Core's unconditional Delete semantics for explicitly selected paths, including current external-activity warnings. Report physical removal after verifying all selected Core-owned resources. Keep an offline, locked or otherwise delayed operation inspectable without another user click.

**Continued conversation and interfaces.** A new user turn obtains a fresh attempt. It may reuse the same native session only through a verified provider/account binding and confirmed agent exit. Any outstanding physical claim continues to protect operations requiring exclusive use. An independent chat or isolated resource can proceed. Model selection, service endpoints and accounts are typed capability references. Reinstallation does not transfer authority over another installation or user's native thread. Only an affected operation can raise a current notice. Show one current outcome and update it in place when the owner publishes changed facts. Dismiss informational history independently of actual safety restrictions. Disable obsolete approvals. An error code never instructs the browser to decide whether a process exited.

## Synchronization without opening a chat

There is exactly one canonical user-facing transcript per conversation, owned by its consumer. For a Harness chat the writer is Harness. The provider journal holds observed native facts and a durable delivery obligation to that chat's owner. A slow consumer does not require a second permanent archive maintained by a competing writer.

1. At admission bind the destination inbox, attempt, chat and context generation. Persist each observed fact with a stable event identity, sequence and causal item references, including a content reference when needed. Preserve the bytes of an attachment or result until the owner durably claims it. A stream notification only tells the subscriber that records exist.
2. Harness receives authorized events even with every browser closed. In one transaction deduplicate the event, update canonical transcript items or pending correlations, and advance the contiguous committed cursor. Only then acknowledge through that cursor. The provider can reclaim the acknowledged segment under its retention policy. If a sender or receiver dies on either side of acknowledgement, repeat delivery of the same facts. A timeout alone cannot evict the only copy of accepted data. Budget exhausted unacknowledged storage by throttling or refusing new work before capacity is exhausted, with an explicit failure at the recording boundary if native output cannot be retained.
3. Assign independent progress per attempt. Fairly read live tails and missing ranges. A newer complete message can render while older pages arrive. A delta waits for its exact item and base revision. A sparse receipt never advances the contiguous acknowledgement past a hole. A closed attempt can have a transcript still catching up. The final history watermark follows durable output drain. Clients read the already-committed local page immediately and subscribe after its revision. A provider outage does not blank locally saved history or make opening the chat responsible for repair.
4. Preserve an early child result with its native child and turn IDs before projecting a parent. Resolve the relationship when the matching start arrives, including after restart. Use a supported read-only native history lookup if needed, scoped to the authorized run. An unresolved parent edge carries no invented attribution. Keep real observations in the owner's authorized inbox, and show permitted content with incomplete attribution when possible. Present a single contextual data gap only for a missing fact the native source can no longer supply. Clear a provisional diagnostic when evidence arrives. An unrecoverable capture gap before the adapter receives a fact is distinct from an unacknowledged event. Name which class occurred.
5. Derive an authorized attempt summary from the same provider transaction. Harness publishes a shared keyed set of summaries to client views. The chat header, workspace rows and navigation counts use one summary for the active attempt. Core supplies participant identity and resource ownership. Collapse a chat and its native run by their explicit association for the ordinary working count. A native-child diagnostic, historical gap, stale membership timestamp or backfill outage cannot rewrite that summary. Carry contact quality and last verified time independently. If the status source itself is unreachable, display the last observation with its age and show stale counts as such. Subscription health cannot certify continuing execution, completion or an empty slot.
6. Read and replay under current actor and ownership checks. Redactions or confirmed deletion remove private payloads and win over delayed delivery. A minimal tombstone can acknowledge discard only for the selected generation. Browser subscribers do not create retention obligations. A delegated private chat exposes only the allowed result and assignment to its parent.

The new release gate reproduces three working chats, one old idle chat-participation row per workspace and a silent history transport for longer than 45 seconds. With valid live status updates, the header, right panel and sidebar must all report three distinct working attempts in aggregate. If live status also disconnects, all views agree on last-known status and freshness. For a history hole of 14 records, make later messages visible immediately, persist the accepted 14 after reconnect with no open tabs, compare the complete transcript by stable IDs and content, and require the marker to disappear. Test child completion before spawn, no spawn, duplicate completion, missing attachment, long backlog, deleted owner and a disk-full subscriber. A native final answer recovered later must remain attributable and visible exactly once.

## What disappears

| Existing mechanism | Replacement |
| --- | --- |
| Separate Worker run journal, provider aggregate and separately updated history index as competing sources of execution truth | One provider transaction for the state, command receipt and ordered event. Native diagnostic logs can survive independently. |
| Harness inferring live execution from transcript history, reconstructing recovery deltas and combining stop bits with tool result certainty | Direct attempt snapshot and replay cursor. Transcript and current status have separate documented owners. |
| Browser-stored recovery request, operator process-exit attestation, Check status/Retry recovery as a prerequisite, stale approval controls | Intrinsically idempotent Stop, server-owned supervision and cleanup. Status remains readable to every authorized client. |
| Per-engine policies for when an OS process has stopped and a global scan of historical runs for each admission | Shared supervisor and indexed reservations. Engine adapters interpret protocol-specific final answers, native children and tool receipts. |
| Browser-driven fan-out of destructive actions and additional confirmations caused by an earlier lost reply | Server-owned selection, logical deletion, exact per-owner receipts and a durable physical cleanup operation. |
| Legacy readers, data conversion, old-run backfill, v1/v2 dual writes and compatibility reinterpretation | An empty v2 execution and chat store, one selected protocol, and explicit rejection of a mismatched installation before admission. |

## Release and relationships with existing work

Selected provider profiles must pass packaged execution on their supported platforms. Codex fixtures cover pending approval versus dispatch, dropped interrupt replies, native child output and pipe draining. Claude fixtures cover queued synthesis, child-owned Bash, status-only results, multi-block messages and redirected native history. Ollama fixtures cover the local agent loop, long MCP decisions across credential renewal and external inference cancellation. A run must never stop a shared model server. Test an independent provider with unrelated IDs and a consumer with no Harness installation. A fixture must also cover a service claiming an unavailable endpoint. Verify actor- and account-scoped discovery, original operation authority, named endpoints, pagination, response sizes, timeouts and resource readiness from the installed artifact.

Cross-feature ownership needs explicit reconciliation because the clean cut supersedes assumptions in existing plans. Use the [provider interface plan](../agent-provider-interface/plan.md) as the source of historical acceptance cases. Replace v1-specific outstanding extraction obligations by explicit owner disposition when v2 is approved. Keep current truth in its feature document until cutover. [Session recovery D4](../harness-session-recovery/plan.md) owns the open isolated Windows storage case. Replay its failure shape against v2 and record separate disposition of the old verification. [Durable jobs D7](../durable-agent-jobs/plan.md) owns general session command/segment semantics. Qualify a vertical slice on a disposable Core first. Exercise send, real native launch, decision, stop, continued chat and active Delete across a crash with every browser closed. Measure native and isolated profiles before committing to a platform default. Implement other engines against the same contract. At the deployment cut, stop accepting v1 work, quiesce or terminate its known writers and verify physical closure before reusing paths. A store reset cannot terminate an existing process. Switch the selected consumer and providers together, initialize empty v2 stores and disable v1 entry points. Remove retired execution data only within the selected installation and reset scope. Abort the switch before reusing old resources if closure or release compatibility cannot be established. A failed v2 release stops new admissions and can be replaced by a known-good v2 build. All first-party writers and readers select the same protocol at cutover.

## Ordinary Stop and exclusive release

On 2026-11-25 the owner selected ordinary workspace editing on macOS with no profile choice. A confirmed exit of the agent reopens the conversation while the provider cleans up descendants in the background. Previously written bytes and independently dispatched external commands keep their own lifetimes. Operations which guarantee physical release or exclusive reuse of a resource require evidence from the specific resource owner.

## Verification and approval

Use fault injection before and after every durable commit, OS launch and external dispatch. Lose, duplicate and reorder acknowledgements, decisions and events. Restart Harness, provider HTTP, supervisor and execution host independently. Combine Stop versus Allow, Delete versus Submit, old terminal versus a new turn, server disconnect during physical cleanup, and database/disk failure with ongoing work. Include a supported idempotent downstream and an irreversible downstream with no status API. In both cases count actual invocations outside Hosty. Assert the exact number of agents, consumed slots and live writers outside the UI. Validate that paid inference or external mutations are never repeated merely to restore chat usability.

With deterministic time and recovered dependencies, require a due operation to converge within two scheduled reconciliation opportunities after the last fault in the healthy fixture. No browser interaction is permitted. Under a permanent fault, require a stable, scoped outcome, bounded retry rate and no accumulating notices. Exercise retained data created by v2 through v2 restart, service upgrade and restoration. Measure real-host stop latency, startup-to-recovery duration, cleanup debt, live responsiveness during backfill and disk growth. Qualify Windows, macOS and supported Linux profiles on their actual release artifact and in a Core-managed, normally authenticated environment. Record unsupported modes and distinguish protocol simulations from real native execution.

For the D8 storage-failure case, keep two native writers running while injecting a failed command commit for one, then exercise an unreadable provider store. The HTTP regression covers a real SQLITE_FULL during a Stop commit and an exact retry after recovery with a test execution driver. The HTTP process can signal the exact supervisor process handle it still owns after a validated Stop fails to commit. The packaged native test observes two independent streams, loss of the selected stream, continued activity in its sibling, absence of a Stop receipt and replay of the original request after storage recovers. A store that cannot be read before authorization yields a retryable error.

The owner approved this plan for implementation on 2026-11-25. The first implementation gate is the owned-execution vertical slice on actual hosts. The ordinary Stop and exclusive resource guarantees follow the owner's subsequent decision recorded above.
