# Provider and Harness reliability review, 2026-11-25

## Finding

A tracked agent process, a conversation, a tool effect and a workspace have different lifetimes. Hosty has repeatedly used a transition in one of them as evidence about another. The final root SDK message closed sessions with live descendants. Missing history made healthy work look unknown. A missing tool result erased affirmative stop evidence. Dropping a permission revision or closing a browser could remove the only path to finish an accepted operation. Several fixes corrected the individual transitions while leaving multiple layers free to interpret the same fact. Another recurring failure was coupling healthy work to a damaged aggregate or a slow archive through a shared read or queue. Startup and release failures have a different cause: tests of a component missed the environment and process boundary used by the installed artifact.

The independent provider boundary itself is viable. Real extraction trials finished work with Harness disconnected. The embedded Worker suffered durability failures before extraction. The strongest case for replacement is the chain of independently persisted interpretations of one execution, plus responsibility for recovery crossing into the browser. A clean redesign can retain provider independence and remove that chain. The [architecture proposal](../features/agent-execution-reliability/plan.md) specifies the ownership, the parts to retire and how to falsify the proposed guarantees.

## November 25 synchronization and sidebar reproduction

The operator supplied a screenshot with three workspace rows each showing one unknown participant, Working 0, a running chat header, an idle row for the selected chat in workspace participation, and a separate unknown native execution row. The open transcript had a history marker for 14 records and a running indicator. The operator reported new messages in all three chats. This is a visible inconsistency. The reported failed deletion occurred near these symptoms. Causation is unestablished.

**Status.** The detail header consumes the selected chat state and stream. The navigation aggregates workspace participant records, selecting between Core and the locally listed chat by timestamp. For linked chat/execution pairs it counts the native execution row. Core and the browser each convert active participant evidence older than 45 seconds to unknown, while idle can persist. The list also overrides status to unknown when the provider's history-contact field is set. A failed installation history subscription can mark contact lost for several bindings at once. These paths do not require that any process stop. Production Harness logs included two subscription-unavailable entries, without attribution to the screenshot's attempts. The log duration describes an attempt's lifetime, so it cannot establish outage duration. The current production operation read did not expose the per-attempt records needed to attribute this particular screenshot to one path. [Workspace aggregation](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/harness/web/src/lib/workspace-navigation.ts#L24-L46) · [Core participation](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/core/src/Haas.Hosty.Core/WorkspaceParticipationEndpoints.cs#L82) · [Feed failure](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/harness/src/agent-providers/history.ts#L209-L234)

A local fixture executed the actual workspace aggregation function from this baseline with three running chat records. Each had a linked native execution and an earlier idle participation row. At a simulated age of 10 seconds the sidebar counted Working 3. With identical inputs at age 46 seconds it counted Working 0 and Unknown 3, with the selected workspace showing idle and unknown. The same fixture at age 10 seconds with a history-contact error also counted Working 0 and Unknown 3. This reproduces the displayed contradiction without changing run state. It establishes two sufficient mechanisms, not which one fired on the production host.

Two contributing code paths deserve independent fixtures. When workspace preparation happens mid-run, Core can create an idle chat participant and a native execution participant without a fresh activity timestamp. The native driver's heartbeat loop visits the workspace list attached to the run, whereas Core also tracks MCP-acquired leases. Separately, the same renewal loop handles an explicit Stop or deadline and a retryable Core transport failure by requesting native cancellation. The latter can actually affect work, even though a stale sidebar alone is only a display symptom. Neither mechanism was confirmed for the three reported runs. [Preparation](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/core/src/Haas.Hosty.Core/WorkspacePreparationOrigin.cs#L79-L87) · [Core lease](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/core/src/Haas.Hosty.Core/CoreAgentMcpLeases.cs#L18-L27) · [Renewal loop](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/packages/agent-provider-runtime/src/native-driver.ts#L299-L322)

**History.** Opening the chat starts its local transcript stream. The loading screen waits for the current chat's stream-ready signal. A “Syncing history” marker counts positions that have not been filled in the consumer's covered ranges. The UI uses a different label when the provider declares a range unavailable. A pending count of 14 does not measure 14 lost chat messages. Current delivery already has background subscriptions and range repair. The proposed architecture makes acknowledged delivery and read availability independent of opening the chat. [Chat readiness](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/harness/web/src/components/assistant-conversation.tsx#L164-L165) · [Gap presentation](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/harness/web/src/components/assistant-conversation.tsx#L119-L125) · [Current recovery contract](../features/harness-history-durability/feature.md#importing-provider-results)

**Child attribution.** The exact warning in the screenshot comes from the Codex child observer. It has seen the child thread ID, but has no accepted record of the spawn that links the thread to the parent call. For a non-start event it emits one incomplete-tools notice and returns before the history read. A later start alone cannot retrieve that already-discarded completion. An ordinary transcript replay can repeat the historical notice after attribution is recovered. The screenshot does not determine the actual ordering or prove root transcript loss. [Codex observer](https://github.com/alex-de-haas/docker-host/blob/c1e69a226f924cf0d6e90c85d79538c6496a2785/apps/codex-provider/src/adapter/codex-children.ts#L34-L50)

The same baseline adapter was bundled unchanged and called with a synthetic child whose verified history contained a final answer. The assertions checked actual history reads and emitted answer/notice events.

| Start, completion | 1 | Yes | No |
| Completion, start | 0 | No | Yes |

## Root causes across releases

| Structural failure | Examples | Design constraint and verification owner |
| --- | --- | --- |
| More than one component decides the terminal state. | #819 terminal SSE preceded control receipt, #826–829 early root result, #835 child ACK reordered, and the pending approval example. | Provider supervisor is the single writer for execution facts. Native final answer and physical exit have separate criteria. D1/D2. |
| Delivery, authority and effects are conflated. | #803 acknowledged data before durability, #819 retry changed arguments, task cancellation removed cleanup rights, #829 revision rotation, #834 publication authority, #837 late terminal and uncertain child admission. | Accepted intent is durable, keyed and scoped to its exact incarnation. Cleanup remains attributable. Every external side effect has a defined dispatch boundary. D1–D3/D7. |
| Updating a view can block execution or overwrite a newer fact. | #803 shared history, #832 disconnected origin, #833 SDK lost retryability and gap closure lost accounting, #851 delayed usage, #853 one bad aggregate affects admission. | Indexed current admission/occupancy and bounded historical reads operate separately. Gap replay only advances the applicable cursor. Live status is an observation from its writer. D1/D4. |
| Process lifetime, workspace lifetime and browser lifetime are entangled. | #819 lease close/acquire race, #836 live source repair, #838 deletion versus retained effects, #843 stale installation, #848 closing the page can leave selected chats behind. | The resource owner accepts and finishes deletion. A durable exact selection and teardown obligation survive disconnect. Verified physical closure gates resource reuse according to actual ownership. D2/D3/D5. |
| A fake transport or unpackaged test misses a release-only failure. | #804 skills on Windows, #805 service origin, #819 nonblocking stdout and HOME redirection, #824–825 Windows path/handle behavior, #830 Unix process group, #831 packaging, #847 PowerShell compilation. | Exercise a shipped artifact and its real OS boundary in the release matrix, with capability-specific admission and readiness. D2/D7/D8. |
| An error code drives several independent UI decisions. | #801 decision-card history, #840 stale connection settings, #848–849 long-running delete and stacked alerts, #852 false recovery during startup, #853 unconfirmed queue pause. | One projection per operation. Historical state never offers a live approval or an inert Retry. Close all browsers during the recovery test. D4–D6. |
| Durable state has no bounded retirement or fair access path. | #803 repeated large journal reads, #833 live work behind historical replay, #851 backlog growth, retained local generations, #853 occupied capacity and traversal of unrelated records. | Use bounded working sets, indexed admission, explicit ownership of retention, storage limits and observable cleanup debt. ## Residual limits and review evidence

- The public Stop snapshot suppresses physical closure when an effect is unresolved. The native driver rejects reconciliation on several distinct prerequisites, including unknown effects. Browser Retry retains most failures. The stop example above exercises the gap after the storage fixes. - #848 records that closing the active Harness page can leave the optional removal of selected attached chats unfinished. Core already has a durable workspace delete operation. Core currently refuses to remove a worktree used by ordinary apps or a running/retained Core. This is a documented dependency and an explicit design decision for active deletion. [PR limitation](https://github.com/alex-de-haas/docker-host/pull/848) · [Workspace deletion contract](../features/workspace-lifecycle-controls/feature.md#unified-delete-and-recovery)
- Two reviewed #833 failures had consequences beyond UI lag. The SDK dropped the retryable flag on a 503, breaking healthy live work and sibling history requests. Closing a gap from a summary snapshot skipped detailed active-time accounting and could undercharge a task budget. Both fixes reached main.
